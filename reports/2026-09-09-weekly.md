## The project has a name: ThreadAtlas

ThreadAtlas compiles ordered documents and conversations into per-entity narratives, connects those
narratives across sources without erasing the source each one came from, and exposes the result two
ways: as retrieval context for an assistant, and as a browsable wiki. Thread is one entity's ordered
run of passages through the documents it appears in; Atlas is what you get when shared entities
connect separate works into regions you can navigate. FactLedger, the name I used with you last
week, now refers only to the layer underneath that holds facts, quotes, dates and provenance.

## The direction changed, and running the pipeline is what changed it

Last week the store's primary content was facts: a subject, a predicate, an object, each carrying a
verbatim quote. I ran the ingestor over the Zep paper and then read its output as a document instead
of as a test result. The fact section was long and repetitive. The per-entity narrative sections,
which I had been treating as a byproduct, read like encyclopedia articles.

So the primary representation is now the **narrative cell**: one short passage about one entity in
one unit of a document, kept in the order the source presents it. An entity's cells in sequence are
its history through a work, and eventually through a corpus. Facts and quotes stay, but as evidence
for verification and for temporal questions, underneath the reading surface rather than on it.
Atomized facts lose the causal and developmental context that makes an answer make sense.

Two things follow. The wiki is no longer a demo at the end of the project; it is the read model, the
normal way both a person and the assistant see the store. And retrieval moves up the schedule, built
as a thin slice alongside the cross-document layer instead of after it, because the access pattern
should shape the structure rather than inherit it.

## Your three questions

**1. Running the papers: done, and the corpus is now redistributable.** The pipeline reads a paper's
PDF, splits it into a verified structure (front matter, body, sections, references), and produces
entities, narrative cells and quote-backed facts. The attached example is the Zep paper run end to
end.

The change since last week is licensing. My original 141 reference papers were mostly under
publisher licenses that forbid redistribution, so the public dataset had to withhold their text and
carry a hash and URL to rebuild it. I have replaced that set with 100 full-text papers on knowledge
graphs and retrieval-augmented generation that are individually verified as Creative Commons
Attribution, gathered from OpenAlex, most cited first. Each one's manifest entry records title,
authors, year, DOI, exact license and source URL, so attribution can be rendered wherever a paper is
quoted. The paper corpus, the extraction, and the resulting wiki can now all be public with nothing
withheld.

**2. Backend: SQLite, one file, no server.** The document's full text is stored once, and every unit
and every fact quote is a character range into it, so any claim resolves to its exact source text
with one slice. Per-document JSONL packages are the write-ahead log the database is built from, and
a public database and a private one come from the same build.

Across documents, entities are not merged. Each document keeps its own version of an entity, and an
edge attaches that version to a parent node that holds only a derived name and summary and asserts
nothing of its own. Re-deciding an identity re-points an edge instead of rewriting records. Adding a
document is append-only, deleting one is a clean delete, every claim keeps its source, and an early
wrong guess about whether two entities are the same never becomes permanent.

**3. Embedder: bge-small-en-v1.5, 384 dimensions, run locally through fastembed.** CPU only, no
PyTorch, downloaded once and then fully offline, and swappable behind a single interface. The end
product has to run on a user's own machine, and at this scale a 384-dimension vector with exact
brute-force search is one matrix multiply, so a larger vector buys nothing.

What is new this week is the granularity, which the move to cells forced. One vector per sentence
inside a narrative cell, plus one per entity, rather than one vector per cell: a whole-cell vector
averages a decisive sentence together with its surroundings and dilutes it. Only the entity name and
the sentence text are embedded. Document and unit labels stay out of the vector because they add
geometric noise, and order and provenance are kept as ordinary relational fields instead. A cell is
scored from its strongest sentence match plus its supporting matches plus the entity match, never an
average. The sentence is the entry point; the cell is what gets returned. Vectors are deletable
derived children of a cell, identified logically rather than by row position, so the packed matrix
is a disposable projection that can be rebuilt at any time.

## One thing I want your read on

There is a system called ASKS, posted on 30 August, that overlaps with this more than anything else
I have found: source-local pages, document-local graph changes, cross-document fusion, and an
embedding-driven hierarchy. I do not think a graph-generated wiki portal is a novel claim and I am
not going to make one. What I think is still mine is the object that accumulates: source-local
narrative states of an entity through ordered units. I plan to write an object-by-object comparison
against ASKS before I build the cross-document layer, and I would like your read on whether that
distinction is narrow enough to defend.
